## 二、通用规约（所有模块必须遵守）

### 2.1 角色定义

系统包含 8 个基础角色，所有 PRD 中的权限矩阵引用以下代号：

| 代号 | 角色 | 说明 |
|------|------|------|
| R-STAFF | 科研人员 | 项目 PI、参与人、成果作者等 |
| R-MANAGER | 科研管理员 | 院所科研处/科教科业务经办 |
| R-LEADER | 院所领导 | 决策视角，主要用数据大屏与审批 |
| R-FINANCE | 财务人员 | 经费到账、报销、凭证、审计 |
| R-AUDITOR | 审计/纪检 | 只读权限，可导出全部数据 |
| R-EXPERT | 评审专家 | 外部/内部评审人，仅见分配的评审任务 |
| R-ETHICS | 伦理委员 | IRB 审查 |
| R-ADMIN | 系统管理员 | 配置、权限、字典维护 |

**权限维度**：RBAC（角色）+ ABAC（属性）双层。ABAC 关键属性包括：所属院所、所属部门、项目 ID、PI ID、密级、时段。

### 2.2 数据字段命名与通用字段

所有表默认包含以下字段（各 PRD 中省略不重复）：

```
id              BIGINT PK AUTO_INCREMENT     主键
code            VARCHAR(64) UNIQUE           业务编号（人可读）
tenant_id       BIGINT NOT NULL              多租户隔离键（院所）
status          VARCHAR(32) NOT NULL         业务状态（各模块自定义枚举）
deleted         TINYINT DEFAULT 0            逻辑删除标记
creator_id      BIGINT NOT NULL              创建人 user_id
modifier_id     BIGINT                       最后修改人
created_at      DATETIME NOT NULL            创建时间
updated_at      DATETIME NOT NULL            更新时间
remark          TEXT                         备注
```

所有金额字段统一使用 `DECIMAL(18,2)`，单位元。所有日期字段统一使用 `DATETIME`，时区 Asia/Shanghai。

### 2.3 通用交互约定

- **列表页**：默认分页 20 条，最多 200；支持列筛选、排序、导出 CSV/XLSX；顶部支持自然语言搜索（AI 能力）。
- **表单页**：字段级校验（前端 + 后端双校验），必填项标红星，异步校验给出加载状态；关键字段变更触发"影响分析"弹窗。
- **审批流**：所有审批类操作必须留下完整流水（who/when/where/what/why），支持撤回、驳回、加签、转办、并行/串行审批。
- **附件**：单文件 ≤ 100MB，格式白名单（PDF/DOCX/XLSX/JPG/PNG/ZIP），存储走对象存储（MinIO 或阿里云 OSS），支持在线预览。
- **通知**：站内消息 + 微信/企业微信 + 邮件 + 短信四级；紧急事项走短信，普通事项走站内。
- **导入导出**：所有列表页支持导出；所有批量数据支持 Excel 模板导入，导入前预览 + 校验 + 冲突提示。
- **操作日志**：所有 CUD 操作记录审计日志，字段级 diff。

### 2.4 AI 能力嵌入规约

AI 能力不是独立入口，而是嵌入业务流程。每个 AI 能力的 PRD 都必须包含以下要素：

- **触发点**：用户在哪个页面、哪个操作下会看到 AI；
- **输入**：AI 消费的上下文（字段 + 历史 + 政策）；
- **输出格式**：结构化 JSON / 自然语言 / 建议卡片；
- **可解释性**：AI 判断必须给出理由和依据条款；
- **置信度**：所有 AI 判断附带 0-1 置信度，低于阈值需人工兜底；
- **人工兜底**：明确写清置信度 < X 时走人工流程；
- **评估指标**：上线后按周监控准确率/召回率/采纳率；
- **数据回流**：用户对 AI 建议的采纳/驳回行为自动进入训练集。

**禁止事项**：AI 不得直接改写用户已提交的数据；AI 不得作为唯一决策依据通过审批。

### 2.5 API 通用规约

- RESTful 风格，路径 `/api/{version}/{module}/{resource}`；
- 所有响应统一 `{ code, message, data, traceId, timestamp }`；
- 分页参数 `page`(1-based) + `size`；返回 `list` + `total`；
- 认证走 JWT + Refresh Token；
- 幂等性：所有 POST/PUT 需支持 `Idempotency-Key` Header；
- 频率限制：普通用户 100 req/min，AI 接口 20 req/min。

### 2.6 状态机命名约定

状态分两层：**持久态 token** 使用大写蛇形，如 `DRAFT`、`SUBMITTED`、`UNDER_REVIEW`、`APPROVED`、`REJECTED`、`EXECUTING`、`COMPLETED`、`TERMINATED`；它是 API、事件、状态迁移与 Mermaid 状态图唯一使用的权威值。数据模型里 `status(...)` 括号内即为 token 序列，如需中文可读，写成 `TOKEN=中文说明` 的映射形式（例：`UNCLAIMED=未认领`），不得用纯中文替代 token。状态迁移在 PRD 中用 Mermaid 状态图描述，节点标签一律取 token。

### 2.7 编号规则

业务编号统一格式：`{前缀}-{年份4位}-{序号6位}`，如 `PRJ-2026-000123`。前缀以 `2.11 编号前缀注册表` 为唯一来源，不由各模块自行命名。序号按租户 + 年份 + 前缀递增。

### 2.8 数据字典管理

所有下拉选项、类型枚举、科目编码等一律走"数据字典"表（sys_dict）由 R-ADMIN 维护，禁止硬编码。字典项支持多语言、生效时段、排序。

### 2.9 验收标准通用条款

每个功能点的验收必须包含以下四类：
- **功能正确性**：正常流程走通，边界场景处理；
- **权限隔离**：跨租户、跨部门、越权访问被拒绝；
- **性能**：列表查询 < 500ms，导出 1 万条 < 30s，AI 响应首字节 < 2s；
- **审计留痕**：所有关键操作在审计日志中可查。

### 2.10 制度规则引擎与确定性合规

科研院所的经费管理办法、绩效考核标准、采购限额、审批权限矩阵等都是**确定性制度**，任何金额、越权、超范围的判断都必须可解释、可审计、可复算。这类判断走**规则引擎**（Drools 或自研 DSL）而不是 LLM；LLM 只负责内容理解、文本抽取与预测建议。二者分工如下：

| 判断类型 | 归属 | 说明 |
|---------|------|------|
| 金额/科目/审批权限是否越权 | 规则引擎 | 输出命中规则号 + 出处条款 + 拒绝/放行原因 |
| 是否触发招投标限额（如 100 万以上） | 规则引擎 | 采购与合同（G）+ 经费（F）共用同一套限额规则 |
| 是否违反"包干制 vs 预算制"科目约束 | 规则引擎 | 预算科目字典（sys_dict）+ 制度规则联合驱动 |
| 发票内容是否属于本项目合理支出 | LLM | 概率判断，附置信度与理由；低置信度回落人工 |
| 合同条款是否存在风险表述 | LLM + 规则 | 规则匹配红线词/金额阈值，LLM 起草风险提示 |
| 评审意见起草、申报书起草 | LLM | 不进入审批硬约束 |

所有制度规则以"制度包"形式版本化管理：`sys_policy_pack(code, name, effective_from, effective_to, dsl_yaml, applied_modules[])`，切换即时生效并保留历史快照；每笔业务单据落地时记录所用 `policy_pack_id`，供事后审计复算。

### 2.11 统一编号中心

项目、任务书、合同、成果、凭证、外协合同、采购申请、资产标签等**所有业务编号**由统一编号中心（`svc-numbering`）分配，避免并发重号与规则漂移。

- 号段服务：Redis + DB 双写，按 `{前缀}-{年4位}-{序6位}` 或 `{前缀}-{年4位}-{院所有序6位}` 分配，业务前缀以本节注册表为准；
- 规则可配：租户 + 前缀 + 分法人维度可组合不同号段；不同分院所可加"法人短码"以避免跨院所串号；
- 幂等取号：同一次申请重试返回同一号；单据作废不回收号；
- 展示与搜索：编号在列表页/详情页全局可搜，AI NL2SQL 优先精确匹配编号。

### 2.12 多法人治理与分级授权

CoNow-AOP 强调"总院—院所两级多法人"是科研院所（尤其中科院/大型集团研究院）的真实治理形态。系统按以下模型支持：

- **组织树**：`ORG` 表支持 `法人类型 ∈ {总院法人, 分院法人, 非法人部门}`；每个法人实体有独立的统一社会信用代码、法人账户、财务并表口径；
- **租户与法人关系**：`tenant_id` 对应一个总院法人（业务系统边界），法人内部再按 `legal_entity_id` 细分；ABAC 增加 `legal_entity` 属性参与权限判断；
- **分级授权**：总院科研处可"看全集团、批跨法人事项"，分院科研处仅"看本法人及其下属部门"；跨法人项目（联合攻关）在**主责法人**登记，参与法人只读；
- **财务并表**：项目、经费、资产、合同在**主责法人**入账，同时按参与法人与参与比例输出**下钻汇总**给总院合并视图；
- **编号策略**：跨法人事项走总院号段，法人内部事项走法人自有号段（参见 2.11）。

### 2.13 安全域与三员管理（涉密）

CoNow 明确划出三张网络安全域：互联网安全域、办公内网安全域、涉密网安全域。科研院所尤其涉密院所必须按域部署与按域授权。

- **业务分级**：所有项目、成果、合同、档案、审批记录均携带 `security_level ∈ {PUBLIC, INTERNAL, SECRET, TOP_SECRET}`；`PUBLIC` 可上互联网，`INTERNAL` 仅在办公内网，`SECRET/TOP_SECRET` 仅在涉密网；
- **信息流向控制**：默认禁止"涉密网 → 办公内网 → 互联网"的**下行流动**，任何跨越必须走"涉密输出审批流"（X 模块），全程留痕并二次核验；反向"互联网 → 涉密网"的上行进入也需审批；
- **三员分立**：系统管理员（负责配置）、安全管理员（负责策略与授权）、审计管理员（负责日志与稽核）三权分立，禁止兼任；R-ADMIN 角色在三员模型下被拆分为三个物理隔离账号；
- **单点登录**：涉密网内独立 IdP，与办公/互联网 IdP 不共享 token；跨域访问统一走"网闸 + 前置机"，业务代码不感知；
- **日志与安全**：所有敏感操作走"字段级 diff + 数字签名 + 不可篡改"审计链；关键操作强制二次身份鉴别（口令 + 硬件 Key）。

### 2.14 移动审批与纸张化套打

Colloa 的"流程审批移动化 + 界面纸张化一键打印"是现场对比高频项。落地要求：

- **移动审批**：所有涉及"审批流"的功能点（P/E/F/R/T/G/A/C/X）必须支持移动端 H5/小程序审批；单据自适应排版、附件拍照上传、手写签名；紧急事项走短信推送；
- **纸张化套打**：申报书、任务书、合同、结题报告、报销凭证、资产标签等**关键纸质材料**必须提供红头/表格套打模板；结构化字段自动回填；模板由 R-ADMIN 维护（`sys_print_template`）；
- **一键打印**：详情页顶部提供打印按钮，默认走套打模板；预览为 PDF；支持"含批注/不含批注"两种版本；
- **归档一致性**：套打输出的 PDF 自动作为归档件写入项目档案（E-10），与结构化字段版本号绑定。

### 2.15 免表填报与数据反哺（人本化）

CoNow 的"人本化"主张——从业务流程自动沉淀数据、避免一线科研人员反复填报——与我们"数据一次录入多次复用"理念一致，作为设计原则贯穿各模块：

- **单一事实来源**：项目、人员、成果、经费、合同、资产的关键字段各仅一处可编辑（Owner 模块），其他模块只读引用或按映射规则带入；
- **自动带入**：新增申报书/任务书/合同/验收材料时，从主数据 + 历史版本自动填充，只让用户复核而不是重填；
- **填报反哺**：任何"上报"或"报送"表格的字段必须**可从数据库直接抽取生成**（如成果年度报送 R-18、学科评估 D-08、上级单位报送模板库 D-07），杜绝二次录入；
- **AI 减负**：LLM 用于文档抽取（发票、任务书、合同）、字段归一化、命名实体识别、去重认领，把"填报工作量"降到最低；
- **数据反哺**：D 模块的画像/趋势/预警结果必须回流到业务操作页（如 PI 画像嵌入到项目详情页、健康分嵌入到审批页），让"沉淀下来的数据"反过来指导动作。

## 三、模块 PRD 统一模板

每个模块 PRD 都按以下 12 节组织，方便对照阅读：

```
1. 模块概述与目标
2. 用户角色与核心场景
3. 用户故事（含优先级）
4. 功能清单与优先级
5. 数据模型（表结构 + 关系）
6. 业务流程与状态机（Mermaid 图）
7. 界面与交互原型（文字描述）
8. AI 能力详规
9. 权限矩阵
10. 接口清单（对外 + 内部）
11. 异常处理与边界场景
12. 验收标准与非功能需求
```
