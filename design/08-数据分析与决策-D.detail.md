## 2. 服务与分层

一模块一套 OLTP 库（PG）+ 一套 OLAP 库（ClickHouse），跨库只存对方 `id`，一致性走 Kafka 事件（`./README.md` §3.1、`../TECH_ARCHITECTURE.md` §五/§八）。**OLTP→OLAP 单向数据流**：大屏/画像重查询走 ClickHouse，避免压垮交易库（ADR-003）。

```
svc-analytics（D 主服务，读写 PG 配置 + 只读 ClickHouse ADS/DWS 取数）
├─ interfaces  : REST（08-...openapi.yaml）/ DTO / Assembler
├─ query       : 指标服务（读 D_METRIC 口径 → 下推 ClickHouse 计算）、报表引擎（D_REPORT→实例）、
│                大屏取数（ADS + 5min 缓存）、下钻路由（ADS→DWS→DWD→业务表）
├─ metric      : 指标口径版本化管理（变更评审、version 递增、历史快照冻结）
├─ schedule    : 订阅调度（frequency/channel 触发 report.scheduled）、报表定时生成、月度态势简报
├─ domain      : 配置聚合根（Metric/Report/Screen/Subscription/Export 模板）
└─ infra       : PG(15) 仓储（配置/元数据）、ClickHouse 只读客户端（取数/下钻）、Redis 缓存、
                 MinIO 快照/导出、Kafka 生产/消费、svc-notify 投递

数据管道（离线/准实时，独立于 svc-analytics 进程）：
业务库(PG/达梦) → Debezium CDC → Kafka → Flink（清洗/维度对齐/质量检查）
   → ODS(每日02:00) → DWD → DWS → ADS(04:00) → 报表刷新(etl.completed)

AI 能力（走 L3，不直接写业务库，PRD 2.4）：
NL2SQL / 政策问答 / 态势简报 / 趋势预测 / 学科图谱 → svc-ai-gateway（LLM 双通道）
   政策问答 → svc-rag（向量检索 Top-5 条款 + 权限过滤） → LLM 组织回答
```

**边界与约束**：
- `svc-analytics` 对 ClickHouse **只读**（取数/下钻/大屏），写入只发生在数仓管道（Flink）；业务元数据（指标/报表/大屏/订阅）读写在 PG。
- NL2SQL 生成的 SQL **不得直连执行**，必经 D 侧"权限改写层"注入过滤（§4.3），再由受控 ClickHouse 只读账号执行；AI 永不写业务/配置库。
- 政策问答/态势简报为概率性输出，只回吐"答案+出处+置信度"，不作唯一决策依据（PRD 2.4）。
- 开放 API（D-17）由 `svc-openapi` 暴露，鉴权走 OAuth2 + Scope，底层复用 `svc-analytics` 查询服务。

## 3. 数仓分层建模

### 3.1 四层职责、粒度、更新频率、新鲜度

| 层 | 职责 | 粒度 | 更新频率 | 数据新鲜度标注 |
|----|------|------|----------|----------------|
| **ODS** 贴源 | 与业务库结构 1:1，仅增量抽取不清洗，作回溯/重算基线 | 源表行级 | 每日 02:00 增量（T+1）；关键表准实时（CDC） | `T_PLUS_1`（默认）/ `REALTIME` |
| **DWD** 明细 | 清洗、标准化、维度对齐、代理键、退化维度、密级/法人字段落地 | 业务过程行级（一次申报/一笔报销/一项成果） | 依赖 ODS，每日批次 | `T_PLUS_1` |
| **DWS** 汇总 | 轻度聚合主题宽表，跨事实拉通（人/项目/部门 年/月） | 主题实体×时间周期 | 依赖 DWD，每日批次 | `T_PLUS_1` |
| **ADS** 应用 | 面向驾驶舱/大屏/报送的成品结果表，直读渲染 | 报表/大屏所需聚合粒度 | 依赖 DWS，每日 04:00 刷新 | `T_PLUS_1`（大屏顶部展示"数据截至日期"） |

- **T+1 主策略**：每日凌晨批量，凌晨 **4 点前完成**（PRD §12）；未完成时大屏顶部红色提醒"数据截至 X 日，今日尚未刷新"（§4.9/§8）。
- **准实时例外**：驾驶舱风险预警、异常报销可走 CDC→Kafka→Flink 流式直写 ADS（`refresh_freq=REALTIME`），但口径仍取自 `D_METRIC`。
- **质量检查**贯穿每层（完整率/一致率/异常值，§4.6）：Flink 作业后置校验，失败落告警并在 `dws_/ads_` 行 `dq_flag=PARTIAL_MISSING`。

### 3.2 核心事实与维度表清单（ClickHouse，DDL 第二部分）

**ODS**：`ods_expense`（← `F_EXPENSE`，示例；其余 `ods_project/ods_output/ods_transfer_deal/ods_asset/...` 同构，1:1 贴源）。

**DWD 事实**（4 张核心，PRD §5.1）：
| 表 | 业务过程 | 主要度量 | 关联维度 |
|----|----------|----------|----------|
| `dwd_project_apply` | 项目申报/立项 | 申报额/批准额 | dim_staff(PI)、dim_department、dim_project_type、dim_time |
| `dwd_expense` | 经费报销 | amount | dim_staff、dim_department、dim_subject、dim_time |
| `dwd_output` | 成果登记 | cited_times、is_ns_series | dim_staff、dim_department、dim_time |
| `dwd_transfer_deal` | 转化交易 | 合同额/到账额/分配额 | dim_staff、dim_department、dim_time（联动 T 模块） |

**DWD 维度**（5 张一致性维度，`ReplacingMergeTree` 取最新快照，均带 `legal_entity_id` 支持多法人下钻）：
`dim_staff`（人员）、`dim_department`（部门/组织树，联动 X 法人树 `_verified`）、`dim_project_type`（项目类型）、`dim_subject`（经费科目）、`dim_time`（时间，年/季/月/周/财年）。

**DWS 宽表**（`SummingMergeTree` 可加度量 / `AggregatingMergeTree` 去重度量）：
`dws_staff_yearly`（人员×年，PI 画像/人均经费）、`dws_project_yearly`（项目×部门×类型×年，立项数/执行率）、`dws_dept_monthly`（部门×月，含 `uniq` 去重活跃 PI 数）。

**ADS 结果**（`MergeTree`，直读渲染）：
`ads_leader_dashboard`（领导驾驶舱 KPI，`legal_entity_id=0`=总院合并视图）、`ads_funding_screen`（经费监督大屏）、`ads_transfer_screen`（成果转化大屏）。

### 3.3 命名规范（对齐 `./README.md` §2.3）

- 数仓表前缀：`ods_`/`dwd_`/`dim_`/`dws_`/`ads_`，小写蛇形；配置表前缀 `D_`（大写蛇形，与业务表同规约）。
- 主键/外键沿用业务语义列名（`*_id`），列存维度键统一 `UInt64`；金额 `Decimal(18,2)`；比例/置信 `Decimal(9,4)`/`Decimal(6,4)`；时间 `Date`/`DateTime`；枚举 `LowCardinality(String)`。
- 每张法人相关表必带 `tenant_id + legal_entity_id`；事实/结果表带 `security_level`；ETL 元数据带 `etl_date`/`etl_load_time`/`_version`。
- 分区键：明细/结果按业务时间 `PARTITION BY toYYYYMM(<date>)`；年度宽表按 `fiscal_year`。`ORDER BY` 首列必为 `tenant_id, legal_entity_id`（多法人合并/下钻主路径）。

## 4. 关键业务规则

### 4.1 指标口径唯一真源 + 口径版本化（D-01/D-07，PRD §11/§12）

- **唯一真源**：一切取数（驾驶舱、报表、大屏、报送、NL2SQL 命中的指标、对标 `metric_code`）均以 `D_METRIC.formula_sql` 为准；**不同报表间口径冲突时以指标字典为准**（PRD §11 报送不一致）。
- **口径版本化**：`D_METRIC` 以 `(code, version)` 唯一，`effective_from/to` 划生活跃区间；同 `code` 仅一个 `effective_to IS NULL AND status='ACTIVE'`（部分唯一索引 `uk_metric_active`）。
- **历史报表留旧口径**：`D_REPORT_INSTANCE.metric_version_snapshot` 冻结生成时各指标版本；复算历史实例按其快照版本取旧 `formula_sql`，**新报表用新口径**；口径变更记录 `caliber_note` + 评审（PRD §11 口径变化、§12 变更评审流程）。
- 指标命名统一、禁止硬编码口径可配项走 `sys_dict`（PRD §12 数据治理 / 2.8）。

### 4.2 下钻链路：ADS → DWS → DWD → 业务表（D-10）

- 每个 `D_METRIC.drill_dims` 声明下钻路径；`/dash/report/instance/{id}/drill` 按 `level` 逐层路由：
  `ADS 结果值 → 去 DWS 主题宽表（部门×月）→ 去 DWD 明细事实（单笔报销/单篇论文）→ 去业务库明细/审批链（svc-* 提供只读接口）`。
- 每一跳由 D 侧受控 ClickHouse 只读账号执行下推 SQL，末级"业务表"跳经 `svc-analytics → svc-{P/E/F/R/T/...}` 只读接口（跨微服务库不建物理外键，§2.3）。
- 审计员可下钻到"明细→审批链→操作日志→上下文快照"（PRD §7.7），依赖 `sys_audit_log` + `e_trace_node`。
- 每一层下钻结果都执行 §4.3 权限过滤与 §4.5 脱敏。

### 4.3 NL2SQL 权限改写层（D-11，PRD §8.1/§11 权限冲突）

**生成的 SQL 必须先经权限改写层注入过滤，绝不直连执行**：

```
LLM 生成候选 SQL（Schema-aware prompt + 指标字典匹配）
   → 权限改写层（确定性，非 LLM）强制追加：
        WHERE tenant_id = <当前用户租户>
          AND legal_entity_id ∈ <用户可见法人集合>      -- ABAC 属性，联动 §4.8/X-10
          AND security_level <= <用户密级>              -- 三网密级过滤（PRD 2.13）
          AND <permission_scope 行级规则：DEPT 追加 dept_id ∈ 本部门>
   → 语法/表白名单校验（仅授权视图/表可查，禁 DROP/UPDATE/跨租户）
   → 受控 ClickHouse 只读账号执行（超时 5s 中断）
   → 结果脱敏（§4.5）→ 记录 generated_sql + rewritten_sql 双留痕（D_QUERY_LOG，可解释可审计）
```

- 改写是**确定性规则**（不依赖 LLM 判断），落 `sys_audit_log`；原始 SQL 与改写 SQL 同存供校验。

### 4.4 语义回读确认（D-11，PRD §8.1）

- `/dash/nl-query` `confirmed=false` 时**不执行**，只回读 `"你是不是想问：…（时间/指标/维度/口径版本）"`，回显匹配到的指标与维度。
- 用户确认（`confirmed=true` + `readback_token`）后才走 §4.3 改写与执行，降低口径歧义；结果附 SQL 可视化供校验。
- 无法映射指标/维度时 → `status=REJECTED_UNMAPPED`，兜底 `"未理解，请联系管理员"`，**不瞎猜不生成**（PRD §11 幻觉）。

### 4.5 数据脱敏（D-09/D-11/D-10，PRD §9）

- 非管理员（R-STAFF/R-MANAGER 等）访问**他人**数据时，敏感字段（手机号/身份证/银行账号）自动掩码，`masked=true` 标注；PI 只能导出本人全量数据。
- 脱敏在执行结果投影层完成（确定性掩码规则），大屏/驾驶舱仅展示聚合值不含个人敏感明细。

### 4.6 数据质量检查（D-02，PRD §6.1/§11）

- Flink 在每层后置校验：**完整率**（非空/行数对账）、**一致率**（跨表口径对账，如报销合计↔经费到账）、**异常值**（阈值外，如执行率>150%、负金额）。
- 检查失败：告警（`etl.completed` payload 带 `dqStatus`）；受影响报表/大屏顶部标注 **"数据存在部分缺失"**（`dq_flag=PARTIAL_MISSING`），不阻断发布但显式提示；报送数据不完整时阻断一键生成并提示（PRD §11）。

### 4.7 规则引擎 vs LLM 分工（对齐 PRD 2.4/2.10、ADR-001）

| 能力 | 归属 | 理由 |
|------|------|------|
| 指标口径计算 / 版本化 / 阈值告警 | **确定性（规则引擎 + D_METRIC）** | 可解释、可复算、可审计 |
| NL2SQL 权限改写 / 表白名单 / 脱敏 / 下钻路由 | **确定性** | 越权/密级/合规不可交给概率模型 |
| NL2SQL 意图解析 + SQL 生成 | **LLM（svc-ai-gateway）** | 自然语言理解；输出必经确定性改写 |
| 政策问答（D-12） | **RAG + LLM（svc-rag）** | 检索 Top-5 条款组织回答；**涉金额/审批权限强制标注"请与科研办确认"**（PRD §8.2），置信度低于阈值回落人工 |
| 态势简报（D-13） | **LLM + 模型** | KPI 环比由确定性算，摘要/建议在确定性数值之上生成 |
| 趋势预测（D-16） | **模型（Prophet+外部指标）** | 预测值/置信区间为参考，不作唯一决策依据 |
| 学科演化图谱（D-15） | **模型（BERTopic+引文网络）** | M3 能力，本文仅登记，产出热度时间轴/交叉桥接 |

### 4.8 多法人合并视图与下钻（D-19，联动 X-10 并表口径）

- **合并口径**：跨法人聚合表统一带 `legal_entity_id`；总院合并视图以 `legal_entity_id=0`（ADS 约定）表示"全集团聚合"。
- **避免重复计入**：跨法人项目**以主责法人入账并表**（`../TECH_ARCHITECTURE.md` §四 2.12），参与法人按比例下钻汇总给总院合并——合并 SQL 只对主责法人求和，参与法人不重复进 ADS 总额。
- **下钻**：总院看全集团 → 点分法人下钻 `WHERE legal_entity_id=<分院>` → 再看本部门/项目明细；ABAC `legal_entity` 属性决定可见法人集合（联动 X-10 法人树与 `dim_department._verified`）。
- 口径可按法人差异化（`D_METRIC.legal_entity_id` 非空=法人专属口径），合并视图取主责法人口径。

### 4.9 大屏渲染与 5min 缓存（D-06，PRD §6.2）

- 前端加载 → `GET /dash/metrics/{code}`/大屏聚合接口 → 服务端查 ADS → **Redis 缓存 5 分钟** → 返回 JSON → ECharts 渲染（60 FPS）。
- `etl.completed` 事件触发缓存主动失效（§5）；`data_as_of` 随响应返回，顶部展示"数据截至日期"，T+1 未刷新时红色提醒。
- 自动轮播 6 组视图（`rotation_seconds`），支持断点续播（布局位点持久化）。

## 5. 数据流与事件（内部 Kafka）

命名 `domain.action`，value 必带 `{ eventId, eventType, occurredAt, tenantId, legalEntityId, traceId, payload }`（`./README.md` §3.1）。

### 5.1 metric.threshold.breach（指标阈值告警 → 触发通知）

```json
{ "eventId":"e-...", "eventType":"metric.threshold.breach",
  "occurredAt":"2026-10-13T02:15:00Z", "tenantId":100, "legalEntityId":0, "traceId":"t-...",
  "payload":{
    "metricCode":"FUNDING_EXEC_RATE", "metricVersion":3,
    "value":0.62, "threshold":0.75, "direction":"BELOW",
    "dimension":{ "departmentId":2001, "fiscalYear":2026 },
    "severity":"HIGH",
    "ruleCode":"RULE-EXEC-RATE-001",
    "notifyRoles":["R-MANAGER","R-FINANCE"],
    "drillPath":["ads_funding_screen","dws_dept_monthly","dwd_expense"]
  } }
```
消费方：`svc-notify`（站内/企微/邮件）、驾驶舱风险清单刷新。`severity` 对齐 F 异常级别 `HIGH/MED/LOW`；`ruleCode` 为命中 `svc-policy` 规则号（可解释、可复算）。

### 5.2 etl.completed（ETL 批次完成 → 刷新缓存 / 质量标注）

```json
{ "eventType":"etl.completed",
  "payload":{
    "layer":"ADS", "batchDate":"2026-10-13",
    "tables":["ads_leader_dashboard","ads_funding_screen","ads_transfer_screen"],
    "rowLoaded":1250000, "durationMs":1830000,
    "dqStatus":{ "completeness":0.998, "consistency":0.9995, "anomalyCount":12,
                 "overall":"PARTIAL_MISSING" },
    "affectedMetricCodes":["ACTIVE_PRJ_CNT","FUNDING_EXEC_RATE"],
    "cacheInvalidatePatterns":["dash:board:*","dash:screen:OVERVIEW:*"]
  } }
```
消费方：`svc-analytics` 主动失效 Redis 5min 缓存；`dqStatus.overall != OK` → 相关报表/大屏顶部标注"数据存在部分缺失"（§4.6）。`completeness/consistency/anomalyCount` 对应完整率/一致率/异常值三类校验。

### 5.3 report.scheduled（定时生成 / 订阅推送 / 月度态势简报）

```json
{ "eventType":"report.scheduled",
  "payload":{
    "trigger":"CRON",
    "reportId":5001, "subscriptionId":null,
    "params":{ "fiscalYear":2026, "departmentId":2001 },
    "channel":null,
    "userId":null,
    "briefType":null
  } }
```
- `trigger`：`CRON`（`D_REPORT.schedule`）/ `SUBSCRIPTION`（订阅）/ `MONTHLY_BRIEF`（D-13）。
- `channel` 订阅触发时为 `EMAIL/WECHAT/INBOX`；`briefType=MONTHLY_BRIEF` 时生成态势简报推送领导。
- 消费方：报表引擎生成 `D_REPORT_INSTANCE`（冻结口径版本 §4.1）→ `svc-notify` 按 `channel` 投递 → 回写 `D_SUBSCRIPTION.last_sent_at`。每月 1 号 08:00 触发 D-13 态势简报（PRD §8.3）。

### 5.4 大屏渲染 5min 缓存流程（PRD §6.2）

```
前端 → GET /api/v1/dash/...(board/metrics)
   → svc-analytics.query：查 Redis(key=dash:{screen}:{tenant}:{le}:{dims})
        命中(<5min) → 直接返回（附 data_as_of）
        未命中     → 读 ClickHouse ADS（受控只读账号，超时 5s）
                    → 结果写 Redis(TTL=300s) → 返回
   前端 ECharts 渲染；关键指标点击 → /dash/report/instance/{id}/drill 逐层下钻
事件旁路：etl.completed → 按 cacheInvalidatePatterns 主动 DEL 缓存（不等 TTL）
```

## 7. 权限与隔离（PRD §9）

### 7.1 驾驶舱差异化布局（同一入口不同角色）

| 角色 | 布局 | 可见范围 |
|------|------|----------|
| R-LEADER | 核心 KPI 卡 + 趋势曲线 + 风险预警 + 今日重要事件 | 全院指标（全部法人，合并视图 `legal_entity_id=0`） |
| R-MANAGER | 待办审批 + 数据变更 + 报表快捷入口 | 全院指标 + 本部门明细；报表设计器 CRUD |
| R-STAFF(PI) | 我的项目/成果/经费概览 | 仅个人数据（可导出本人全量，他人脱敏） |
| R-FINANCE | 到账/支出/异常 | 财务类指标查看/CRUD |
| R-AUDITOR | 追溯查询入口 + 关注事项 | 全院（含下钻到审批链/日志） |

- 差异化通过预置 `D_REPORT(type=DASHBOARD)` + `permission_scope` + 角色映射实现；大屏编辑权限见 PRD §9（R-MANAGER CRUD、R-LEADER 只读、R-AUDITOR 不可编辑）。

### 7.2 数据隔离三键（读 ClickHouse + 写 PG 一致遵循）

- **RBAC + ABAC 双层**：ABAC 判定键 `tenant_id + legal_entity_id + security_level`（外加 dept/PI/时段）（`../TECH_ARCHITECTURE.md` §七）。
- 密级：`security_level ∈ {PUBLIC,INTERNAL,SECRET,TOP_SECRET}` 参与每次读取的网关+数据层双重过滤；涉密指标/明细仅在对应安全域可读。
- 法人：`legal_entity_id` 决定合并视图 vs 分法人下钻（§4.8 联动 X-10）；NL2SQL/报表/大屏一律注入。
- 开放 API（D-17）：`svc-openapi` OAuth2 + Scope（`dash:metric:read`/`dash:report:read`/`dash:export:write` 等），Scope 映射角色可见范围，外部调用只读取不落库。

## 8. 异常与边界（PRD §11）

| 场景 | 处理策略 |
|------|----------|
| **数据延迟** | 大屏/报表顶部展示 `data_as_of`；T+1 04:00 未刷新（无 `etl.completed`）→ 红色提醒"数据截至 X 日，今日尚未刷新"；缓存不返回过期于阈值的数据而不标注 |
| **指标口径变化** | 历史报表保留旧口径（`metric_version_snapshot`），新报表用新口径，展示 `caliber_note` 变更说明（§4.1） |
| **NL2SQL 幻觉** | 无法映射指标/维度 → `REJECTED_UNMAPPED`，兜底"未理解，请联系管理员"，**不生成不执行**（§4.4） |
| **NL2SQL 权限冲突** | 生成 SQL 必经权限改写层注入 `tenant_id/legal_entity_id/security_level` 过滤后才执行（§4.3），越权/白名单外直接拒绝（41005） |
| **查询超时** | 5s 未返回中断，提示"建议缩小范围（时间/部门）"，`D_QUERY_LOG.status=TIMEOUT`；`504` 兜底 |
| **报送数据不一致** | 跨报表口径冲突 → 以 `D_METRIC` 指标字典为唯一真源重算（41008）；报送字段免表可抽（schema_json） |
| **数据质量下降** | ETL 检查失败告警，报表/大屏顶部标"数据存在部分缺失"（`dq_flag=PARTIAL_MISSING`），不完整时阻断报送一键生成（§4.6） |
| **政策问答低置信** | 置信度 < 阈值 → `status=FALLBACK` 回落人工；涉金额/审批权限强制"请与科研办确认"（§4.7） |
| **法人可见越权** | 请求 `legal_entity_id` 不在用户可见集合 → 41011（`403`），合并视图仅总院级可请求 `legal_entity_id=0` |

## 9. 非功能与性能（PRD §12）

- **性能**：驾驶舱加载 < 1.5s（ADS 直读 + Redis 5min 缓存）；大屏渲染 60 FPS（ECharts 客户端 + 预聚合结果，轮播取数走缓存）；常规报表 5s 内返回；NL2SQL 端到端 < 5s（超时中断）；ClickHouse 列存高吞吐聚合。
- **数据新鲜度**：T+1，每日凌晨 4 点前完成 ETL 灌至 ADS；关键预警支持 CDC 准实时（`REALTIME`）。
- **可用性**：大屏自动轮播 + 断点续播；报表导出 CSV/EXCEL/PDF(/XML 报文)；邮件/企业微信/站内消息三通道订阅。
- **规模基线（验收）**：指标 60+ 核心指标、预置 20+ 常用报表 + 5+ 大屏模板 + 4+ 上级报送模板；NL2SQL 覆盖常见查询 75%（执行准确率≥75%）；政策问答准确率 ≥ 85%。
- **数据治理**：指标命名统一避免口径歧义；所有报表标注数据源/生成时间/责任部门（`data_as_of`+`generated_at`+`owner_role`）；建立指标变更评审流程（version 递增留痕）。
- **可审计**：NL2SQL 原始 SQL + 改写 SQL 双留痕；导出/报送走 `sys_audit_log` 字段级 diff + 哈希链；命中阈值记 `sys_rule_hit` 可复算。
- **信创**：PG 侧按 `./README.md` §2.4 达梦替换；ClickHouse 侧信创替代路径 Apache Doris（列存语法近似）。

## 10. 待细化问题（定稿前须闭环）
