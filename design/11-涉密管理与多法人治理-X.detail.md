## 2. 服务与分层

```
       前端(法人树/合并看板/密级授权/输出审批/安全审计)
                              │ Bearer JWT + X-MFA-Assert + network_zone(来源域,网关注入) + traceId
                              ▼
   ┌───────────────────────────────────────────────────────────────┐
   │  svc-gateway / zone-guard  (三网访问判定前置，X-02)             │  ← 增加延迟 < 50ms
   │  取对象 security_level → 查 X_SECURITY_POLICY 可见域 →          │
   │  network_zone∈可见域? 且 actor.granted_level≥object.level 且 MFA → 字段级放行/拒绝+risk 埋点
   └──────┬───────────────┬───────────────┬───────────────┬─────────┘
          ▼               ▼               ▼               ▼
     svc-iam(三员)     svc-identity      svc-policy      svc-audit
     RBAC+ABAC,       独立 IdP,         密级策略/流向    X_SEC_LOG SM3
     sys_admin_duty   涉密网不共享       规则(x_flow_     哈希链+
     隔离,MFA         token,硬件 Key    audit 编排)      sys_audit_log
          │               │               │               │
          └──────────── Kafka 事件总线 domain.action (跨域拒绝 / 输出放行 / 授权变更 / 密级变更) ───────────┘
                              │
   svc-security(X 域服务)：法人治理编排(读写 sys_legal_entity) / 分级授权(X_ACCESS_GRANT) / 并表口径(联动 F/D)
                              │
                 涉密网内本地模型(信创)：X-13 AI 疑似涉密识别，语料/模型不出域
```

**分层约定（各服务同构）**：
- `controller`：参数/幂等（Idempotency-Key）/二次鉴别（X-MFA-Assert）/权限校验（法人+密级+三员职责），DTO↔领域模型；OpenAPI 落此层。
- `application`：判定编排、`x_flow_audit` 状态机驱动、并表口径计算（预聚合）、涉密人员审查/清退用例、Saga 发起（授权→事件→各业务服务收敛）。
- `domain`：三网判定算法、密级继承/降密/解密规则、三员分立裁决、并表去重口径；值对象（密级枚举、网络域枚举、SM3 摘要值、比例 NUMERIC(6,4)）。
- `infrastructure`：PostgreSQL 15 持久化（达梦差异见 DDL 顶部 §2.4）、Kafka 生产/消费、HSM/密码机对接（SM2 签名、SM3 链、SM4 加密）、逻辑外键跨服务客户端（S/A/F/D）、涉密网本地 LLM 推理适配器（X-13）。

**职责边界（三权分立落到服务）**：
- `zone-guard` 只做**确定性判定与放行/拒绝**，不写业务数据；判定结果异步落 `X_SEC_LOG`。
- `svc-identity` 是涉密网**独立 IdP**（不与办公/互联网共享 token，TECH_ARCH §七）；`X_ACCESS_GRANT` 的 `granted_level` 随其签发。
- `svc-policy` 加载 `X_SECURITY_POLICY`（经 `policy_pack_id` 与 `sys_policy_pack` 同源），裁决写 `sys_rule_hit`，可解释可复算。
- `svc-audit` 维护 `X_SEC_LOG` 哈希链与 `sys_audit_log` 签名；**审计管理员只读稽核、不可删改**（改策略的人删不了日志）。
- AI（X-13）在涉密网内本地推理，**只回吐提示**，绝不写 `security_level`/`classify_status`。

## 3. 数据模型明细

> **先复用后独有**：法人=`sys_legal_entity`（+`sys_org` 树），输出审批=`x_flow_audit`，通用审计=`sys_audit_log`，三员=`sys_admin_duty`（见 §1.2）。以下仅列本模块独有 4 表；均含 §2.1 通用列（`id/code/tenant_id/status/deleted/creator_id/modifier_id/created_at/updated_at/remark`，**`X_SEC_LOG` 为追加日志例外**）与治理列 `legal_entity_id NOT NULL`、`security_level DEFAULT 'INTERNAL'`。完整定义见 `11-涉密管理与多法人治理-X.ddl.sql`。

### 3.1 X_SECURITY_POLICY（密级/流向策略，版本化制度包的一种；SEC-年-序）

| 列 | 类型 | 说明 |
|----|------|------|
| version | INT | 策略版本号，同 code 多版本并存 |
| effective_from / effective_to | DATE / DATE | 生效区间；NULL=当前有效 |
| matrix_json | JSONB | 每 security_level 的 `visible_zones/role_whitelist/can_export/can_cross_net/desensitize`（zone-guard 判定依据）；完整性由 SM3 校验 |
| applied_modules | VARCHAR(128)[] | 生效模块集合 {P,E,F,R,T,G,A,C,D…}（达梦改 ','分隔/JSON） |
| policy_pack_id | BIGINT | 逻辑联动 `sys_policy_pack.id`，可复算 |
| status | VARCHAR(32) | DRAFT/ACTIVE/SUPERSEDED（对齐 sys_policy_pack） |

唯一：`uk_secpolicy_code_ver(tenant_id,code,version) WHERE deleted=0`；`uk_secpolicy_active(tenant_id,applied_modules) WHERE status='ACTIVE'`（同集合唯一 ACTIVE）。

### 3.2 X_ACCESS_GRANT（授权与密级许可，ABAC 属性源；SEC-年-序）

| 列 | 类型 | 说明 |
|----|------|------|
| subject_user_id | BIGINT FK sys_user(id) | 被授权人 |
| scope_type | VARCHAR(16) | LEGAL_ENTITY/DEPT/PROJECT/SECURITY_LEVEL |

| granted_level | VARCHAR(16) | 授予可见最高密级 PUBLIC/INTERNAL/SECRET/TOP_SECRET |
| network_zone | VARCHAR(16) | INTERNET/OFFICE/SECRET_NET |

### 3.3 X_SEC_LOG（涉密专用安全日志，append-only，SM3 哈希链）

| 列 | 类型 | 说明 |

### 3.5 关键关系（ER）

```

sys_admin_duty(user 唯一) ── 三员分立裁决 ──> X_ACCESS_GRANT / X_SECURITY_POLICY
```

### 3.6 密级 token 与状态机对齐（PRD §6.2）

- **对象/可见密级集合**（`security_level`/`granted_level`，静态分级，README 2.13）：`PUBLIC/INTERNAL/SECRET/TOP_SECRET`。
- **定/降/解密工作态**（`classify_status`，落 `X_PERSONNEL_SEC` 及单据，流程过渡态）：`UNCLASSIFIED 待定密 / DOWN_CLASSIFY 降密中 / DECLASSIFY 解密中`。
- 状态机：`UNCLASSIFIED →（人工定密，AI 仅提示）→ SECRET →（升密审批）→ TOP_SECRET`；`SECRET →（降密申请）DOWN_CLASSIFY →（审批）INTERNAL 或 DECLASSIFY →（审批）PUBLIC`。**工作态走完才回写对象 `security_level`**，两者严格分离，DDL/OpenAPI 注释均强调勿混淆。

## 4. 关键业务规则

### 4.1 三网访问判定算法（zone-guard 前置，X-02/04）

```
请求(带 network_zone 来源域, actor, 目标 object, traceId)
 1. 取 object.security_level（缺失按最保守 INTERNAL）
 2. 查 X_SECURITY_POLICY(status=ACTIVE, applied_modules∋object 模块) → matrix[security_level].visible_zones
 3. network_zone ∈ visible_zones ?
       否 → DENY：写 X_SEC_LOG(result=DENY, risk_flag≥1) + 返回 403（业务码）
            【不暴露对象存在性/细节，防探测】；连续越权 → risk_flag=2 高危告警
       是 → 4. 取 actor 有效授权 X_ACCESS_GRANT(subject=actor, status=EFFECTIVE, now∈[valid_from,valid_to])
              max(granted_level) ≥ object.security_level ?
                否 → DENY（授权不足）→ 同 3 否分支埋点
                是 → 5. 若 object.security_level ≥ SECRET：校验 MFA 达标(mfa_bound=1 ∧ X-MFA-Assert 通过)
                        不达标 → 403（要求二次鉴别）
                        达标 → ALLOW：字段级放行
    6. ALLOW 仍做字段级过滤：matrix 未授权字段脱敏/占位；写 X_SEC_LOG(result=ALLOW) 异步入链
```
- **默认可见最小化、跨域默认拒绝**（PRD 目标 1）。判定为纯确定性逻辑，**不经 LLM**。
- 判定耗时纳入 SLO：< 50ms 增加延迟（§9）；策略矩阵 Redis 缓存 + `policy_pack_id` 版本号失效。

### 4.2 信息流向控制与涉密输出审批（X-05/06，复用 x_flow_audit）

- **默认禁止跨域**：涉密网→办公内网→互联网的下行、互联网→涉密网的上行一律默认禁止；例外走 `POST /security/export` 创建 `x_flow_audit`（direction=DOWN/UP，APPLIED）。
- **双审**：项目负责人初审（APPLIED→PRE_REVIEW）+ 安全管理员复审（PRE_REVIEW→SEC_REVIEW）；审批人须与申请人不同人（`approver ≠ applicant` 后端强校验）。
- **二次鉴别放行**：`/release` 必须 `X-MFA-Assert` 通过方置 RELEASED，记 `second_verifier_id` 与 `release_scope`。
- **内容指纹防篡改**：申请登记 `payload_digest=SM3(拟输出脱敏内容)`；放行时 `/release` 传 `actualPayloadDigest`，与审批指纹**不一致则二次拦截（409）+ risk_flag=2 告警**，绝不放行。
- **留痕**：全流程写 `x_flow_audit` + `X_SEC_LOG`（CROSS_NET/EXPORT），可追溯（US-X-03/04）。

### 4.3 三员分立（X-03，复用 sys_admin_duty）

- **物理隔离**：`sys_admin_duty` 上 `uk_admin_duty_user(user_id)` 强制一人只任一类三员；系统/安全/审计三权分立，禁止兼任。
- **能力铁律**：配置的人（SYS_ADMIN）看不到内容；看内容的人按其密级许可；改策略的人（SEC_ADMIN）删不了日志；稽核的人（AUDIT_ADMIN）只读、不可删改日志——**三权互相制衡**（PRD §9）。
- **兼任即冻结**：巡检发现同一自然人跨 `sys_user` 多账号规避唯一约束而事实兼任 → 立即 `X_ACCESS_GRANT` 冻结 + risk_flag=2 告警（§8）。
- R-ADMIN 不再是超级权限：涉密正文对 SYS_ADMIN/AUDIT_ADMIN 不可见（除非其另有密级许可，见 §7 矩阵）。

### 4.4 密级继承与降密/解密（X-14，AI 绝不自动定密/降密）

- **继承**：派生对象（附件、成果、下游单据）默认继承父对象 `security_level`；继承只升不降（子对象不得低于父对象密级），除非显式解密审批。
- **降密/解密**：`/security/classify(op=DOWN_CLASSIFY|DECLASSIFY)` 置 `classify_status=DOWN_CLASSIFY|DECLASSIFY` → 人工审批（安全管理员 + 定密责任人）→ 通过回写对象 `security_level`（如 SECRET→INTERNAL→PUBLIC）或人员 `granted_level`。
- **铁律（US-X-09 / PRD §8）**：AI（X-13）**绝不自动定密、绝不自动降密**；定密/降密/解密永远是人工决定，AI 仅提示片段+建议密级+依据。
- 升密（SECRET→TOP_SECRET）亦走审批；未定密内容默认按 INTERNAL 保守处理（§8）。

### 4.5 法人树分级授权（X-08/09）

- **树**：法人层级由 `sys_org.parent_id`（org_type=TOTAL_INSTITUTE/BRANCH_INSTITUTE）与 `sys_legal_entity` 1:1 承载；`/governance/entity` 输出总院—分院树。
- **分级授权（ABAC tenant_id+legal_entity_id）**：
  - 总院（R-LEADER/总院科研处）：看全量、批跨法人事项。
  - 分院（分院科研处）：看本法人及下属部门；越权访问其他法人 → 403（README 2.12）。
- **主责法人登记**：跨法人联合攻关事项在**主责法人登记**（`LegalEntityNode.asPrimary`），参与法人**只读**本所相关部分（`X_ACCESS_GRANT(scope=PROJECT, 参与法人)` 授只读/按密级）。
- 跨法人事项编号走总院号段，法人内部事项走法人自有号段（README 2.11）。

### 4.6 并表口径与下钻（X-10，联动 F/D，避免重复计入）

- **口径**：`/governance/consolidate?level=merge` 总院合并总量；`level=drill&legalEntityId=…` 分法人下钻。
- **去重规则**：项目/经费/资产/合同**以主责法人为准**计入合并值；参与法人按**分摊比例**（`rows[].allocRatio`，如成本按使用率、收入按合同分成）下钻，**不重复计入**收入/资产（§8 多法人重复统计）。
- 与 A 的折旧分摊口径一致：A 在主责法人计提、按使用比例拆分（`A_DEPRECIATION.alloc_project_ids`）；F 平行记账/全成本与 X 并表口径对齐评审（TECH_ARCH 待决问题 2）。
- 预聚合物化视图 + CDC，保证查询 < 1s（§9）。

### 4.7 涉密人员入职审查 / 在岗复审 / 离岗清退（X-11/12，联动 07）

- **入职审查**：`personnel/review(op=ONBOARD_REVIEW)` 核保密审查+培训（`training_records`）→ 置 `secret_eligible=1`、授 `granted_level`（同步签发 `X_ACCESS_GRANT`）、`status=GRANTED`。
- **在岗复审**：`op=INPOST_RE_REVIEW` 刷新 `review_date/next_review_date`；逾期未复审 → `status=RE_REVIEW/FROZEN`，授权冻结（§8）。
- **离岗清退**：`op=LEAVE_CLEARANCE` 联动 07 离职（S-11/离职交接）；`leave_clearance` **三要素（载体归还/权限回收/保密承诺）全部完成**方可 `CLEARED_OUT`。
- **权限与载体收敛**：未完成清退 → `X_ACCESS_GRANT` 自动 `FROZEN`（降级为“存在该项目”的**只读脱敏占位**，不可读涉密正文）；涉密载体（联动 10 `A_ASSET>=SECRET`）与介质（X-12）回收/销毁登记，未归还则不允许 CLEARED_OUT。

### 4.8 信创降级（X-15）

- **判定**：运行环境（OS/DB/中间件/CPU/密码机）信创符合性由部署探测上报；非信创或密码算法不可用时，**禁用涉密子能力**（SECRET/TOP_SECRET 相关入口灰化）。
- **降级行为**：`/security/policy|grant|export|classify|personnel/review` 在非信创环境返回业务码拒绝（503/403），并灰化前端入口，**避免在不合规栈处理涉密数据**。
- 多法人治理（非密级部分）不受信创涉密开关影响，可独立运行（§10 可交付性）。
- 密码算法：SM3（`X_SEC_LOG` 哈希链）、SM2（审批签名/`sys_audit_log.sig`）、SM4（涉密正文/附件密文存储，涉密网内）。

### 4.9 审计与哈希链（X-07）

- 判定/越权/流向/授权/密级变更埋点 `X_SEC_LOG`；**异步链**写入不阻塞主流程（§5）。
- 每条 `hash_self = SM3(hash_prev ‖ canonical(业务字段))`；链式追加，`hash_prev` 取上一条 `hash_self`。
- 稽核查询校验区间链完整性；`chainIntact=false` 即触发最高级安全告警 + 转**只读取证模式**（禁止写入，保留现场）。
- 与通用 `sys_audit_log`（SM2 签名）通过 `traceId` 关联，形成“数据变更 + 安全判定”双链。

### 4.10 规则引擎 vs LLM 分工（对齐 TECH_ARCH ADR-001 / PRD 2.4）

| 能力 | 归属 | 说明 |
|------|------|------|
| 三网访问判定（zone/level/MFA） | **确定性策略 + zone-guard** | 100% 拒绝跨域越权；不经模型 |
| 信息流向 / 输出审批状态机 / 内容指纹比对 | **规则引擎 + 事务** | 双审、指纹不符拦截，可复算 |
| 三员分立 / 法人分级授权 / 并表去重口径 | **确定性策略 + ABAC** | sys_admin_duty 唯一约束、主责法人为准 |
| 密级继承 / 降密 / 解密 | **人工 + 规则** | AI 绝不参与定密/降密 |
| **X-13 AI 疑似涉密识别** | **LLM（涉密网内本地部署）** | 仅提示“疑似涉密片段+建议密级+命中规则”，**不定密**；**漏报优先（宁可误报）**，人工确认；低置信不拦截只提示；语料/模型不出域 |

> 硬约束：密级/流向/授权/并表一律由策略与网关决定；LLM 只产“提示”，不得写 `security_level`/`classify_status`。AI 接口限流 20 req/min（429）。

## 7. 权限矩阵（三员分立，PRD §9）

| 能力 | 系统管理员 SYS_ADMIN | 安全管理员 SEC_ADMIN | 审计管理员 AUDIT_ADMIN | R-LEADER | R-AUDITOR |
|------|---|---|---|---|---|
| 用户/字典/系统配置 | ● | 读 | 读 | | |
| 密级策略/授权/流向规则 | 无 | ● | 读 | 审批 | 读 |
| **查看涉密正文** | **无权** | 按其密级许可 | 无权（仅元数据/日志） | 按其密级许可 | 授权域内读 |
| 审计日志/告警 | 无（不可删改） | 读 | ● 稽核 | 读 | 读 |
| 法人树/并表口径 | 配置 | 授权 | 读 | ● | 读 |
| 定密/降密/解密 | 无 | 发起+审批（与定密责任人） | 读 | 审批 | 读 |

- 跨法人数据按 `legal_entity` ABAC 隔离（README 2.12，§4.5）。

## 8. 异常与边界场景

| 场景 | 处理 |
|------|------|
| 跨域越权访问（zone 与 level 不匹配） | DENY + risk 告警 + `X_SEC_LOG`；对本人不暴露对象细节（403 业务码，防探测）；连续尝试 risk_flag=2（§4.1） |
| AI 误判/漏判定密 | 定密/降密永远人工，AI 仅提示；未定密内容默认 INTERNAL 保守处理；漏报优先（§4.4/4.10） |
| 三员兼任 | `sys_admin_duty(user_id)` 唯一约束拦截；跨账号事实兼任巡检命中即冻结授权 + 高危告警（§4.3） |
| 日志被篡改 / 哈希链断裂 | `chainIntact=false` → 最高级安全告警 + 只读取证模式（禁写保现场），保留 `hash_prev/hash_self` 供取证（§4.9） |
| 脱密输出内容指纹不符 | `/release` 比对 `actualPayloadDigest` ≠ 审批 `payload_digest` → 二次拦截 409 + risk_flag=2，绝不放行（§4.2） |
| 多法人重复统计 | 并表以主责法人为准，参与法人按分摊比例，抵销收入/资产重复计入（§4.6） |
| 人员离岗未清退 | 三要素（载体/权限/承诺）未完成 → `X_ACCESS_GRANT` 自动 FROZEN，降级只读脱敏占位，不得读涉密正文（§4.7） |
| 涉密模块在非信创环境 | 灰化入口 + 业务码拒绝，避免不合规栈处理涉密数据（§4.8） |
| 策略缺失（无 ACTIVE） | zone-guard 回落内置保守默认：SECRET/TOP_SECRET 一律拒绝，PUBLIC/INTERNAL 按角色基线（§4.1） |
| 双审同人 / 申请人自批 | 后端强校验 `approver≠applicant`，非法迁移拒绝（§4.2） |
| 跨法人越权 | 分院访问其他法人 → 403；主责登记、参与只读（§4.5） |

## 9. 非功能与合规（对齐 PRD §12）

- **性能**：zone-guard 判定增加延迟 **< 50ms**（策略矩阵 Redis 缓存 + `(subject,status)`/`(granted_level,network_zone)` 索引 + 版本号失效）；并表查询 **< 1s**（物化预聚合 + CDC）；`X_SEC_LOG` 写入**异步**（Kafka 入链，不阻塞主流程）。
- **安全**：三员职责隔离；涉密正文对 SYS/AUDIT 管理员不可见（除非密级许可）；二次身份鉴别强制；审计防篡改（SM3 哈希链校验 + SM2 签名）。
- **合规**：满足《保守国家秘密法》、涉密信息系统分级保护（BMB 相关）、**等保三级**；全栈信创 + 国产密码算法 **SM2/SM3/SM4**（TECH_ARCH ADR-007 三网物理隔离+独立 IdP）；支持但不绑定底层栈（对齐 CoNow“信创/不绑定 WinTel”）。
- **可审计**：判定/授权/流向/密级变更全留痕，`policy_pack_id` 快照 + 命中 `sys_rule_hit` 可复算。
- **信创方言**：PostgreSQL 15 + 达梦差异注记（IDENTITY/TIMESTAMP WITH TIME ZONE/JSONB→CLOB/BOOLEAN→SMALLINT/数组→分隔串/部分唯一索引降级复合唯一，见 DDL 顶部 §2.4）。
- **限流**：普通 100 req/min，AI（X-13）20 req/min（429）。

## 10. 可交付性（对齐 PRD §12 / 竞品不绑定）

- **涉密可整体关闭**：非涉密单位经配置开关关闭 X 涉密子能力（zone-guard 涉密判定、策略/授权/输出/清退/日志），**仅保留多法人治理**（法人树/分级授权/并表）。关闭后 `security_level` 恒按 INTERNAL/PUBLIC 处理，涉密端点返回业务码不可用。
